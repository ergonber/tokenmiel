# ADR-002: ERC-1155 como token standard

**Status:** Accepted
**Date:** 2026-05-19
**Author:** Dany Hidalgo F.
**Tags:** smart-contracts, token-standard, erc-1155

---

## Context

El sistema necesita un estándar de token para representar lotes de commodities tokenizados (cada lote es una unidad económica distinta con metadatos propios — variedad, apiario, cosecha, certificados de calidad). Cada lote tiene múltiples poseedores fungibles entre sí dentro del mismo lote.

Cuatro opciones evaluadas: ERC-20 por lote, ERC-1155 multi-token, ERC-3643 (T-REX), ERC-721 NFT.

---

## Decision

**Adoptar ERC-1155 (Multi-Token Standard) como estándar único.**

- Un solo contrato `AssetVault.sol` gestiona todos los lotes
- Cada lote es un `tokenId` distinto
- Balance de un usuario en un `tokenId` representa kg poseídos (escalados por granularidad)
- Granularidad: **1 token = 0.5 kg** (constante `GRAMOS_POR_TOKEN = 500`)

---

## Alternatives considered

### ERC-20 por lote
- ✅ Familiar, máxima compatibilidad de wallets
- ❌ Proliferación masiva de contratos (un deploy por lote)
- ❌ Costo de deployment alto, indexer complejo
- ❌ Gestión administrativa engorrosa

### ERC-3643 (T-REX Standard)
- ✅ Compliance-first by design, modular compliance
- ✅ Adoptado por instituciones (Société Générale FORGE)
- ❌ Diseñado para tokens transferibles entre verified holders (mercado secundario)
- ❌ Nuestro modelo es **solo primario** — la maquinaria de T-REX nunca se usa
- ❌ ERC-20 base, requiere un contrato por variedad de asset
- ❌ Costo de auditoría significativamente mayor
- ❌ Complejidad innecesaria

### ERC-721 (NFT)
- ❌ NFT son no-fungibles, pero dentro del lote los kg son intercambiables
- ❌ No aplica al caso

### ERC-6960 (Dual Layer Token)
- ❌ Experimental, baja adopción, pool de auditores muy pequeño

---

## Consequences

### Positive

- **Un solo contrato** para todos los lotes — deployment eficiente, auditoría única.
- **Batch operations** nativas (mint múltiple, transfer múltiple en una transacción).
- **Soporte universal en wallets:** MetaMask, Coinbase Wallet, Rainbow, Rabby, etc.
- **Maduro y ampliamente auditado** (estándar Ethereum bien establecido).
- **Hook `_update()`** disponible para custom logic en transfers (compliance hook embebido).
- **Storage eficiente:** `tokenId → balance` por usuario.

### Negative

- **Sin compliance features built-in.** Hay que implementar custom hooks (KYC validation, no-P2P).
- **Sin decimals nativos.** Balance es entero — la conversión a unidades físicas (kg) se hace en presentación.

### Neutral

- Reglas de transferencia personalizadas vía override `_update()`.
- Eventos estándar (`TransferSingle`, `TransferBatch`) reconocidos por todos los indexers.

---

## Implementation notes

### Granularidad
- **1 token = 0.5 kg** para miel
- Constante: `uint256 constant GRAMOS_POR_TOKEN = 500`
- Para 1 kg → mint 2 tokens. Para 100 kg → mint 200 tokens.
- Razón de la granularidad de 0.5 kg:
  - B2C ticket bajo accesible (USD 18-30 para impulso)
  - Frasco gourmet estándar 500g como anclaje físico
  - Supply moderado (lote 200 kg = 400 tokens)
  - Para otros assets futuros, granularidad configurable por categoría

### Herencias OpenZeppelin v5
```solidity
AssetVault is ERC1155, ERC1155Supply, ERC1155Pausable, AccessControl, ReentrancyGuard
```

### Override crítico: `_update()`
Bloquear todo transfer que no sea mint o burn:

```solidity
function _update(address from, address to, uint256[] memory ids, uint256[] memory values)
    internal override(ERC1155, ERC1155Supply, ERC1155Pausable)
{
    bool isMint = (from == address(0));
    bool isBurn = (to == address(0));

    if (!isMint && !isBurn) revert TransferP2PNoPermitido();

    if (isMint) {
        if (!kycRegistry.canMint(to)) revert NotKYCVerified();
        // ... más validaciones
    }

    if (isBurn) {
        if (msg.sender != address(redemptionManager)) revert OnlyRedemptionCanBurn();
    }

    super._update(from, to, ids, values);
}
```

### Sin decimals
ERC-1155 no tiene decimals nativos. Balance es entero. La conversión a unidades físicas se hace en la capa de presentación (frontend) con constantes documentadas.

### URI (metadata)
Aunque no es crítico para MVP, considerar metadata URI por `tokenId` apuntando a Arweave con metadata del lote (variedad, apiario, certificados). Esto permite que wallets muestren info rica del token.
